# 压测场景设计最佳实践

> **难度**: ⭐⭐⭐⭐ | **重要程度**: ⭐⭐⭐⭐⭐

## 📚 概述

压测场景设计是性能测试的核心，好的场景设计能够真实反映系统性能，发现潜在问题。本文总结压测场景设计的最佳实践。

## 🎯 一、压测目标设定

### 1.1 明确压测目的

#### 基准测试（Baseline Test）
- **目的**: 建立性能基准
- **场景**: 单用户或少量用户
- **关注**: 响应时间、资源消耗

#### 负载测试（Load Test）
- **目的**: 验证系统在预期负载下的表现
- **场景**: 模拟正常业务量
- **关注**: TPS、响应时间、错误率

#### 压力测试（Stress Test）
- **目的**: 找到系统的极限
- **场景**: 逐步增加负载直到系统崩溃
- **关注**: 最大TPS、崩溃点、恢复能力

#### 稳定性测试（Soak Test）
- **目的**: 验证系统长时间运行的稳定性
- **场景**: 正常负载下持续运行（如24小时）
- **关注**: 内存泄漏、资源耗尽

#### 峰值测试（Spike Test）
- **目的**: 验证系统应对突发流量的能力
- **场景**: 短时间内流量激增
- **关注**: 系统响应、恢复时间

### 1.2 设定性能指标

#### 响应时间指标

| 指标 | 优秀 | 良好 | 可接受 | 需优化 |
|------|------|------|--------|--------|
| **平均响应时间** | <200ms | <500ms | <1s | >1s |
| **95%响应时间** | <500ms | <1s | <2s | >2s |
| **99%响应时间** | <1s | <2s | <3s | >3s |

#### 吞吐量指标

```
目标TPS = 日活用户 × 人均请求次数 / (24 × 3600 × 峰值系数)

示例：
日活：100万
人均请求：50次
峰值系数：0.2（假设20%流量集中在4.8小时）

目标TPS = 1,000,000 × 50 / (24 × 3600 × 0.2) ≈ 2894
```

#### 错误率指标

- **可用性**: >99.9%（错误率<0.1%）
- **高可用**: >99.99%（错误率<0.01%）


## 💡 二、场景设计方法

### 2.1 业务场景分析🔥

#### 步骤1：梳理业务流程

```
电商系统核心流程：
1. 用户登录
2. 浏览商品列表
3. 搜索商品
4. 查看商品详情
5. 加入购物车
6. 提交订单
7. 支付
```

#### 步骤2：分析流量分布

```
根据生产日志分析：
- 浏览商品列表：40%
- 搜索商品：20%
- 查看商品详情：25%
- 加入购物车：10%
- 提交订单：4%
- 支付：1%
```

#### 步骤3：确定用户行为路径

```
路径1（浏览型用户 - 70%）：
登录 → 浏览列表 → 查看详情 → 退出

路径2（购物型用户 - 25%）：
登录 → 搜索 → 查看详情 → 加购物车 → 继续浏览 → 退出

路径3（下单型用户 - 5%）：
登录 → 搜索 → 查看详情 → 加购物车 → 提交订单 → 支付
```

### 2.2 负载模型设计🔥

#### 恒定负载

```
适用场景：验证系统在稳定负载下的表现

JMeter配置：
线程数：1000
Ramp-Up：60秒
持续时间：10分钟

Gatling配置：
constantUsersPerSec(100).during(10.minutes)
```

#### 阶梯负载

```
适用场景：找到系统性能拐点

阶段1：100用户，持续5分钟
阶段2：200用户，持续5分钟
阶段3：500用户，持续5分钟
阶段4：1000用户，持续5分钟

Gatling配置：
incrementUsersPerSec(100)
  .times(4)
  .eachLevelLasting(5.minutes)
  .separatedByRampsLasting(1.minute)
  .startingFrom(100)
```

#### 波浪负载

```
适用场景：模拟真实流量波动

Gatling配置：
rampUsersPerSec(10).to(100).during(5.minutes),
constantUsersPerSec(100).during(10.minutes),
rampUsersPerSec(100).to(10).during(5.minutes)
```

#### 尖峰负载

```
适用场景：秒杀、抢购等突发流量

Gatling配置：
nothingFor(10.seconds),
atOnceUsers(5000),  // 瞬间5000用户
constantUsersPerSec(100).during(5.minutes)
```

### 2.3 思考时间设计

#### 为什么需要思考时间？

```
❌ 没有思考时间：
用户登录 → 立即浏览 → 立即搜索 → 立即下单
（不符合真实场景，压力过大）

✅ 有思考时间：
用户登录 → 等待2-5秒 → 浏览 → 等待3-8秒 → 搜索
（符合真实用户行为）
```

#### 思考时间设置原则

```
操作类型          建议思考时间
-------------------------------
页面跳转          2-5秒
浏览内容          3-10秒
填写表单          5-15秒
阅读详情          10-30秒
```

#### JMeter配置

```
添加 → 定时器 → Gaussian Random Timer
偏移量：3000ms
标准差：1000ms
```

#### Gatling配置

```scala
.pause(2, 5)  // 2-5秒随机
.pause(3.seconds)  // 固定3秒
```


## 📊 三、数据准备策略

### 3.1 测试数据量估算🔥

#### 基本原则

```
测试数据量 = 并发用户数 × 循环次数 × 安全系数

示例：
并发用户：1000
循环次数：10
安全系数：2（避免数据重复）

所需数据量 = 1000 × 10 × 2 = 20,000条
```

### 3.2 数据准备方法

#### 方法1：CSV文件

**优点**: 简单、易维护
**缺点**: 大数据量时性能差

```csv
# users.csv
userId,username,password,email
1,user1,pass1,user1@example.com
2,user2,pass2,user2@example.com
...
```

#### 方法2：数据库

**优点**: 数据量大、查询灵活
**缺点**: 增加数据库压力

```sql
-- 准备测试用户
INSERT INTO test_users (username, password)
SELECT 
  CONCAT('user', n),
  MD5(CONCAT('pass', n))
FROM 
  (SELECT @row := @row + 1 AS n 
   FROM information_schema.tables, (SELECT @row := 0) r 
   LIMIT 100000) numbers;
```

#### 方法3：随机生成

**优点**: 无需准备数据、数据量无限
**缺点**: 可能不符合业务规则

```scala
// Gatling
val userFeeder = Iterator.continually(Map(
  "userId" -> Random.nextInt(100000),
  "username" -> s"user${Random.nextInt(100000)}",
  "email" -> s"user${Random.nextInt(100000)}@example.com"
))
```

### 3.3 数据隔离策略

#### 读写分离

```
读操作：使用共享数据（circular模式）
写操作：使用独立数据（random模式）

JMeter：
CSV Data Set Config
- 读操作：Sharing mode = All threads
- 写操作：Sharing mode = Current thread

Gatling：
val readFeeder = csv("read_data.csv").circular
val writeFeeder = csv("write_data.csv").random
```

#### 数据清理

```sql
-- 压测前清理
DELETE FROM test_orders WHERE created_at < DATE_SUB(NOW(), INTERVAL 1 DAY);

-- 压测后清理
DELETE FROM test_orders WHERE user_id LIKE 'test_%';
```

### 3.4 数据一致性

#### 问题场景

```
场景：库存扣减
问题：1000个用户同时购买，但库存只有100

解决方案：
1. 准备足够库存
2. 使用不同商品ID
3. 接受部分失败（符合真实场景）
```

#### 最佳实践

```
1. 数据充足性：数据量 >= 并发数 × 循环次数 × 2
2. 数据真实性：符合生产数据分布
3. 数据独立性：避免数据竞争
4. 数据可重复：支持多次压测
```


## 🔍 四、结果分析技巧

### 4.1 关键指标分析🔥

#### 响应时间分析

```
正常情况：
- 平均响应时间稳定
- 95%和99%响应时间在可接受范围
- 响应时间分布呈正态分布

异常情况：
- 响应时间持续上升（资源耗尽）
- 响应时间波动大（GC频繁、锁竞争）
- 长尾效应明显（慢查询、超时）
```

#### TPS分析

```
正常情况：
- TPS随并发数线性增长
- 达到峰值后保持稳定

异常情况：
- TPS上不去（瓶颈）
- TPS下降（系统过载）
- TPS波动（不稳定）
```

#### 错误率分析

```
常见错误类型：
- 5xx错误：服务器问题
- 4xx错误：客户端问题（可能是数据问题）
- 超时错误：响应慢或网络问题
- 连接错误：连接池满、网络问题
```

### 4.2 性能瓶颈定位

#### 系统资源监控

```bash
# CPU监控
top -H -p <pid>

# 内存监控
free -m
jmap -heap <pid>

# IO监控
iostat -x 1

# 网络监控
iftop
netstat -an | grep ESTABLISHED | wc -l
```

#### 应用层监控

```
1. JVM监控
   - GC频率和时长
   - 堆内存使用
   - 线程数

2. 数据库监控
   - 慢查询
   - 连接数
   - 锁等待

3. 缓存监控
   - 命中率
   - 内存使用
   - 连接数

4. 中间件监控
   - 消息队列积压
   - 连接池使用率
```

#### 常见瓶颈及解决方案

| 瓶颈类型 | 现象 | 解决方案 |
|---------|------|---------|
| **CPU瓶颈** | CPU使用率>80% | 优化算法、增加机器 |
| **内存瓶颈** | 频繁GC、OOM | 增加内存、优化代码 |
| **IO瓶颈** | IO等待高 | SSD、优化查询 |
| **数据库瓶颈** | 慢查询多 | 索引优化、读写分离 |
| **网络瓶颈** | 带宽打满 | 增加带宽、CDN |
| **锁竞争** | 线程阻塞 | 优化锁粒度、无锁化 |

### 4.3 报告编写

#### 报告结构

```
1. 测试概述
   - 测试目的
   - 测试环境
   - 测试时间

2. 测试场景
   - 场景描述
   - 负载模型
   - 数据准备

3. 测试结果
   - 关键指标
   - 性能图表
   - 错误统计

4. 问题分析
   - 性能瓶颈
   - 根因分析
   - 优化建议

5. 结论
   - 是否达标
   - 风险评估
   - 后续计划
```

#### 关键数据展示

```
测试结果汇总表：

指标              目标值    实际值    是否达标
-------------------------------------------------
平均响应时间      <500ms    320ms     ✅
95%响应时间       <1000ms   850ms     ✅
99%响应时间       <2000ms   1650ms    ✅
最大TPS           >1000     1250      ✅
错误率            <1%       0.3%      ✅
```

- [ ] 思考时间设置合理
- [ ] 数据参数化正确

### 5.2 压测中监控

#### 实时监控指标

```
1. 压测工具指标
   - 当前TPS
   - 响应时间
   - 错误率

2. 系统资源指标
   - CPU使用率

#### 数据收集

```

### 5.4 常见错误

#### 错误1：压测环境不真实

```
❌ 错误做法：
- 单机压测分布式系统
- 使用开发环境配置
- 数据量远小于生产

✅ 正确做法：
- 环境配置与生产一致
- 数据量接近生产规模
- 网络环境相似
```

#### 错误2：场景设计不合理

```
❌ 错误做法：
- 所有用户执行相同操作
- 没有思考时间
- 流量分布不真实

✅ 正确做法：
- 多种用户行为路径
- 合理的思考时间
- 符合真实流量分布
```

#### 错误3：只看TPS不看其他指标

```
❌ 错误做法：
- TPS很高但错误率也很高
- 忽略响应时间
- 不关注系统资源

✅ 正确做法：
- 综合评估多个指标
- 关注用户体验（响应时间）
- 监控系统健康度
```

#### 错误4：数据准备不充分

```
❌ 错误做法：
- 数据量不足导致重复
- 数据不符合业务规则
- 忽略数据清理

✅ 正确做法：
- 准备充足的测试数据
- 数据符合真实分布
- 压测后及时清理
```


## 🎯 六、典型场景案例

### 6.1 电商秒杀场景

#### 场景特点

```
- 瞬间高并发
- 读多写少
- 库存竞争激烈
- 对响应时间要求高
```

#### 压测设计

```
1. 预热阶段（5分钟）
   - 100用户浏览商品
   - 建立缓存

2. 秒杀阶段（1分钟）
   - 瞬间5000用户
   - 疯狂点击抢购按钮

3. 恢复阶段（5分钟）
   - 逐步降低到正常流量
   - 观察系统恢复情况
```

#### 关注点

```
- 缓存击穿
- 数据库锁竞争
- 库存超卖
- 系统恢复能力
```

### 6.2 社交媒体场景

#### 场景特点

```
- 读写比例高（90:10）
- 热点数据明显
- 实时性要求高
```

#### 压测设计

```
用户行为分布：
- 刷新feed流：50%
- 查看详情：30%
- 点赞评论：15%
- 发布内容：5%

负载模型：
- 基础负载：1000用户
- 波动范围：800-1500用户
- 持续时间：2小时
```

### 6.3 支付系统场景

#### 场景特点

```
- 对数据一致性要求极高
- 不能有任何错误
- 响应时间要求严格
```

#### 压测设计

```
1. 正常支付流程
   - 创建订单
   - 调用支付接口
   - 查询支付结果
   - 更新订单状态

2. 异常场景
   - 支付超时
   - 支付失败
   - 重复支付

3. 并发控制
   - 逐步加压
   - 严格监控错误率
   - 错误率>0.1%立即停止
```

### 6.4 API网关场景

#### 场景特点

```
- 流量入口
- 多种API混合
- 需要限流熔断
```

#### 压测设计

```
API分布：
- 高频API（/api/user/info）：40%
- 中频API（/api/order/list）：30%
- 低频API（/api/payment）：20%
- 其他API：10%

测试重点：
- 限流是否生效
- 熔断是否正常
- 降级策略是否合理
```
